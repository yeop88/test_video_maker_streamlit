# 작업 큐에서 두 작업이 동시에 돌던 문제 (2026-10-31)

## 증상

사용 중 큐 기록(`workdir/gen_queue.json`):

| 작업 | 넣은 시각 | 시작 | 끝 |
|---|---|---|---|
| AI 대본 (비행기 쇼츠) | 23:10:26 | 23:10:26 | 23:15:10 |
| AI 대본 (같은 작업, 다시 만들기) | 23:14:02 | **23:14:02** | 23:17:00 |
| AI 장면 1 | 23:16:15 | 23:16:16 | (진행 중) |
| AI 장면 2 | 23:16:18 | **23:17:00** | (진행 중, 장면 1과 동시) |

첫 작업이 도는 동안 다음 작업이 대기하지 않고 바로 시작됨. 서버 프로세스는 하나.

## 원인

- 큐 처리는 서버 프로세스 안의 스레드 하나가 맡고, 그 스레드는 `jobqueue` 모듈 전역(`_runner`)에 저장되어 있었음.
- Streamlit은 불러온 파일이 바뀌면 다음 실행 때 앱 폴더의 모듈을 전부 `sys.modules`에서 지우고 다시 불러온다 (`streamlit/watcher/local_sources_watcher.py`).
- 서버를 켠 뒤(22:53) 0.7.0 릴리즈를 하며 `shorts_maker/__init__.py`의 버전을 고침(23:08:06) → 다음 화면 실행 때 `jobqueue`가 새 모듈 객체로 다시 만들어짐 → `_runner`가 비어 있어 `ensure_runner()`가 처리 스레드를 하나 더 띄움. 예전 스레드도 그대로 살아 있어 두 스레드가 같은 큐 파일에서 각자 대기 작업을 꺼냄.
- 추가 위험: 다시 불러올 때 `ensure_runner()`가 「진행 중」 항목을 「대기」로 되돌려, 예전 스레드가 처리 중인 작업을 새 스레드가 한 번 더 처리할 수 있었음 (재현 테스트에서 실제로 발생).
- 같은 이유로 불러 둔 Whisper·Chatterbox(`tasks._models`), AI 생성 프로세스(`generate.service`), 자원 사용량 측정 스레드도 두 벌이 될 수 있었음.

## 고친 것

1. `.streamlit/config.toml`: `folderWatchBlacklist = ["*/shorts_maker/*", "*/gen/*"]` — 앱 패키지는 「바뀌면 다시 불러오기」에서 뺌 (Streamlit이 절대 경로로 fnmatch 하므로 `*/폴더/*` 꼴이어야 맞음, `FolderBlackList`로 확인). `app.py`, `ui/`는 그대로 바로 반영.
2. 프로세스에 하나만 있어야 하는 것은 `sys.__dict__`에 둠: `jobqueue._STATE`(처리 스레드, 잠금, 진행 상황, 취소 신호, 일시정지, 처리 함수 목록), `tasks._SHARED`(불러 둔 모델), `generate._SHARED`(생성 프로세스, GPU 잠금), `system._SHARED`(측정 스레드·기록). `ensure_runner()`는 이름이 `job-queue`인 살아 있는 스레드가 있으면 새로 띄우지 않음.
3. 「진행 중 → 대기」 되돌리기는 처리 스레드가 큐 처리 권리(잠금 파일 `workdir/gen_queue.lock`, Windows `msvcrt.locking` / 그 밖 `fcntl.flock`)를 잡은 뒤 한 번만. 같은 작업 폴더를 쓰는 서버가 둘이면 잠금을 잡은 쪽만 처리하고 다른 쪽은 기다림.
4. 다른 서버에서 취소한 작업도 `report()`가 1초마다 큐 파일을 확인해 멈춤. 큐 파일 임시 이름을 프로세스·스레드마다 다르게 하고, Windows에서 바꿔치기가 막히면 잠깐 뒤 다시 시도.
