## 테스트 방법

테스트 영상은 직접 만듭니다. 대본과 각 대사의 실제 시작 시간(정답)을 정확히 알아야 수치로 검증할 수 있기 때문입니다.

- **음성**: Edge TTS로 대본을 읽은 음성
- **배경음악**: 220Hz 화음(220 / 277 / 330Hz), 소리 크기가 2Hz로 출렁임
- **화면**: ffmpeg `testsrc2` 테스트 화면

전체 흐름은 앱(`app.py`)과 같은 `pipeline` 함수를 같은 순서로 호출합니다.

## 전체 실행 기록

각 실행에서 무엇을 발견했고 어떻게 고쳤는지 순서대로 적었습니다. 고친 내용은 [CHANGELOG.md](../../CHANGELOG.md)에도 정리했습니다.

### 사전 테스트 A — 영어 영상 1개 (23초)

- **결과**: 끝까지 동작함. 1080×1920 영상이 나옴
- **발견한 문제**
  1. 언어 감지 결과가 빈 값. 30초 조각 처리 모드에서는 Whisper가 언어 정보를 돌려주지 않음
  2. 번역에 한자가 섞임 ("먼저 앞半身이 돌고")
  3. 더빙 보고서에 "0.0초 잘림", "-0.0초 잘림"처럼 잘리지 않은 대사도 잘림으로 표시됨
- **수정**: Whisper `detect_language`를 따로 호출해 언어를 고정, 번역 규칙에 "한글로만"을 추가하고 한자·가나가 섞인 줄은 다시 요청, 잘림은 실제 넘친 길이로 계산하고 0.1초 미만은 표시하지 않음

### 사전 테스트 B — 영어 영상 + 한국어 영상

- **결과**: 통과. 영어는 `english`로 감지되고 한자 없이 번역됨. 한국어는 번역을 건너뛰고 Edge TTS 더빙과 원본 소리 깔기로 렌더링됨
- Streamlit 화면도 확인: AppTest로 첫 화면이 오류 없이 뜨고, 실제 서버 상태 확인(`/_stcore/health`) 응답이 `ok`

### 1차 검증 — 3개 모두 통과 (그러나 문제 발견)

- 처음 기준으로는 3개 모두 통과
- **발견한 문제**: 결과를 직접 보니 T3(63초)의 대사 시간이 틀어져 있었음
  - 첫 구간(0.7~26.5초)에 대사 5개가 몰림
  - 이후 구간은 너무 짧게 잡힘 (6초짜리 대사가 1.9초 구간에 들어감) → 더빙 5개가 빨라지고 2개가 잘림
  - 원인: 30초가 넘는 음성에서 transformers 조각 처리(`chunk_length_s`)의 문장 단위 타임스탬프가 부정확함
- **진단 실험**: T3 음성으로 두 방식 비교
  - (a) 단어 단위 타임스탬프 → 정답과 0.5초 안팎으로 일치
  - (b) 조각 없이 Whisper 긴 음성 처리 → 30초 이후 틀어지고, 빈 대사와 오류 발생
- **수정**: 단어 단위 타임스탬프를 받아 문장부호와 쉼을 기준으로 직접 문장 단위로 묶도록 변경
- **기준 보강**: "대사 시작 정확도" 검사 추가 (1차 기준으로는 이 문제를 잡지 못했음)

### 2차 검증 — 3개 모두 실패 (검사 방식 오류)

- 새로 넣은 타이밍 검사에서 3개 모두 실패하고, 결과 저장(JSON)에서도 `numpy.bool_` 오류가 남
- **원인**: 검사 방식이 잘못됨. 이제 대사를 문장 단위로 나누므로 한 줄 안의 두 번째 문장(예: "안녕하세요." 다음 "오늘은…")은 원래 줄의 시작 시간과 당연히 다른데, 이것을 오류로 셈
- **수정 (검사)**: "실제 대사마다 근처에서 시작하는 구간이 있는가"와 "구간 시작이 실제 말소리 안에 있는가" 두 가지로 바꿈. JSON 저장 전에 bool로 변환

### 3차 검증 — 3개 모두 실패 (실제 버그)

- **발견한 문제**: 세 테스트 모두 첫 대사가 0.0초에서 시작함 (실제는 약 1초, 오차 0.9~1.21초). 나머지 대사는 오차 0.1초 이내
  - 원인: 단어 타임스탬프가 첫 단어 시작을 음성 조각 맨 앞으로 잡음 → 화자가 말하기 1초 전에 더빙이 먼저 나옴
- T2의 4.92초 오차는 버그가 아님: 일본어 결과에 문장부호가 없어서, 쉼이 짧은 두 문장이 한 구간으로 묶였고 그 구간의 시작은 정확함
- **수정**: 소리 크기(RMS)로 실제 말소리가 시작되는 지점에 구간 시작을 맞춤 (`snap_to_speech`). 기준값은 잡음 바닥과 큰 소리 사이 25% 지점이라 배경음이 깔린 영상에서도 동작
- **수정 (검사)**: 앞 구간에 묶인 대사는 "묶임"으로 따로 셈

### 4차 검증 — 3개 모두 통과 (그러나 문제 발견)

- 대사 시작 오차가 모두 0.07초 이하로 개선됨. T3도 잘린 더빙이 2개에서 0개로 줄어듦
- **발견한 문제**: 더빙을 다시 들어 보니 Chatterbox가 아라비아 숫자를 제대로 읽지 못함
  - "15번씩 3세트" → "금비반씩 달새 세트", "30초" → "텔즈초"
  - 원인: Whisper는 한국어를 숫자로 받아쓰고, 한국어 영상은 번역을 건너뛰므로 숫자가 그대로 더빙 엔진에 들어감
- **수정**: 더빙에 넣는 대사만 숫자를 한글 읽기로 변환 (`korean_numbers.py`, 자막은 숫자 그대로). 번·개·명·세트처럼 고유어로 세는 단위 앞에서는 고유어("열다섯 번", "세 세트"), 나머지는 한자어("삼십 초", "구백 엔"), 6월·10월은 "유월"·"시월". 단위 테스트 11개 사례 통과

### 5차 검증 — 3개 모두 통과 (그러나 문제 2개 발견)

- 숫자 읽기 효과 확인: 다시 들었을 때 "15번씩", "30초"로 정확히 들림
- **발견한 문제 1**: T3을 다시 받아쓴 결과에 "팔꿈치를… 생각보다 어렵지 않네요."가 두 번 나옴
  - 해당 구간(38~58초)만 잘라 받아쓰면 반복이 없음 → 더빙 문제가 아니라 Whisper가 30초 조각을 이어 붙이면서 시간이 48.3초에서 40.0초로 되돌아가 같은 단어가 다시 들어간 것
  - 사용자 영상을 받아쓸 때도 생길 수 있는 문제
- **발견한 문제 2**: "오늘부터 바로 따라 해봐야겠어요" 끝에 Chatterbox가 "네, 또."를 덧붙임 (실제 더빙 소리)
  - 지금까지 만든 더빙의 글자당 길이를 측정: 정상은 0.14~0.20초, 덧붙인 경우는 0.31초와 0.40초
- **수정**: 시간이 거꾸로 가는 단어를 버리도록 함. Chatterbox 더빙이 예상 길이(글자 수 × 0.17초 + 0.4초)의 1.5배를 넘으면 최대 3번 다시 생성해서 가장 짧은 결과를 사용
- **기준 보강**: 더빙 유사도 기준을 0.6에서 0.85로 올리고, "덧붙은 말 없음"(글자 수 1.1배 이하) 검사 추가. 이 두 문제는 이전 기준으로는 통과해 버렸음

### 6차 검증 — T3 실패

- T1, T2 통과
- **T3 실패**: 원본 받아쓰기에서 "처음에는 15번씩 3세트로…" 대사가 통째로 빠짐 (인식 유사도 0.977 → 0.918)
- 원본 데이터를 확인하니, 반복 제거 코드 탓이 아니라 **Whisper 출력에서부터 빠져 있었음**. transformers의 겹쳐 이어 붙이는 조각 처리는 경계 대사가 두 번 들어가기도(5차), 빠지기도 함(6차)
- **수정**: 조각 처리를 직접 구현. 음성을 15~28초 사이의 가장 조용한 지점에서 겹치지 않게 자르고 조각마다 따로 인식 (`split_at_silence`)

### 7차 검증 — T3 실패

- T1, T2 통과
- **T3 실패**: 이번에는 다른 대사 2개가 빠짐 ("하루에 몇 번 정도 하면 될까요?", "그 다음 동작은 무엇인가요?")
- 조각 처리 방식을 바꿔도 빠짐 → 조각 경계 문제가 아니라 **Whisper가 짧은 문장을 가끔 건너뛰는 특성**. 실행마다 빠지는 대사가 다름
- 앞 대사를 건너뛴 자리만큼 다음 첫 단어 시간이 늘어나 잡히는 현상도 확인 ("처음에는"이 22.6초부터 시작으로 잡힘, 실제는 26.3초)
- **수정**
  - 소리 크기로 말소리 구간을 찾고, 받아쓴 단어가 30% 미만으로 덮는 구간은 그 부분만 다시 인식해서 채워 넣음 (Whisper의 흔한 환각 문구 "감사합니다" 등은 버림, 기존 단어와 겹치는 단어도 버림)
  - 비정상적으로 긴 단어는 끝 시간 기준으로 1.2초로 줄임
  - Chatterbox 다시 생성 기준을 1.5배에서 1.25배로 조임 (짧은 덧붙임 "응.", "해."가 남아 있었음)

### 8차 검증 — 3개 모두 통과 (그러나 T2 퇴보 발견)

- T3: 빠졌던 대사가 모두 복구됨 (15개 구간, 시작 오차 0.01~0.06초)
- **발견한 문제**: T2(일본어)의 "오늘 도쿄에서… 왔어요" 구간이 1.2초(5.5~6.7초)로 잡혀 더빙이 1.35배로 빨라짐
  - 원인: 일본어처럼 띄어쓰기가 없는 언어는 Whisper가 문장 전체를 한 "단어"로 돌려주는데(예: 2.18~6.7초), 7차에서 넣은 "1.2초로 줄이기"가 이것을 잘라 버림
- **수정**: 단어가 늘어났는지를 글자 수 대비 길이로 판단. 허용 길이는 1.2초와 글자당 0.35초 중 큰 값 ("처음에는" 4글자 4.4초는 줄이고, 일본어 20글자 4.5초는 그대로 둠)

## 남은 한계와 주의할 점

검증에서 기준은 통과했지만 알고 있는 한계입니다.

1. **문장 중간이 나뉘는 경우가 있음**: T3의 "…30초를 버티는" / "거예요."처럼, 말하는 중간에 0.4초 이상 쉬면 문장이 나뉠 수 있습니다. 자막과 더빙은 정상적으로 나오지만, 2단계 표에서 직접 합치는 기능은 아직 없습니다.
2. **화자가 여러 명이어도 목소리는 하나**: Chatterbox는 긴 대사들을 이어 붙여 목소리 샘플을 만듭니다. T3처럼 남녀가 대화하는 영상도 한 목소리로 더빙됩니다.
3. **번역 품질은 LLM에 따라 다름**: 9B 모델은 가끔 틀립니다 (사전 테스트에서 "righting reflex(정위 반사)"를 "올바른 반사"로 번역). 2단계에서 고치거나 더 큰 모델을 고르세요.
4. **Chatterbox 결과는 실행마다 다름**: 같은 대사도 길이가 달라져서, 빨라진 더빙 수가 실행마다 바뀝니다 (T3 기준 3~6개).
5. **테스트 영상은 합성 음성**: 실제 영상(여러 사람이 겹쳐 말하기, 큰 배경음악, 잡음, 노래)은 이 검증에 포함되지 않았습니다.
6. **화면 클릭 테스트는 하지 않음**: 검증은 앱과 같은 `pipeline` 함수를 직접 호출했습니다. Streamlit 화면은 첫 화면이 오류 없이 뜨는지와 서버 응답까지만 확인했습니다 (AppTest는 파일 업로드를 지원하지 않음).
7. **배경음악 유지 비율은 근사값**: 더빙 목소리에도 220Hz 성분이 있어서 1보다 크게 나올 수 있습니다. "배경음악이 사라지지 않았다"는 확인용입니다.
8. **배포**: GPU와 로컬 Ollama가 필요해서 Streamlit Community Cloud에서는 실행할 수 없습니다.
